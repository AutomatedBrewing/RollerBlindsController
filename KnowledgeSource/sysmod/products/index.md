# SYSMOD Product

* [Base Architecture](base-architecture.md) - The Base Architecture is a description of the architectural and technical decisions that are preset at the project start, documenting constraints and setting the abstraction level for system requirements.
* [Domain Knowledge](domain-knowledge.md) - The Domain Knowledge is a specification of the domain objects used by the Use Case Activities, Requirements, and System Architectures, defining the data and physical entities known by the system.
* [Functional Architecture](functional-architecture.md) - The Functional Architecture consists of functional elements, functional interfaces, flows, and architecture decisions, providing a technology-independent functional description of the system.
* [Logical Architecture](logical-architecture.md) - The Logical Architecture specifies the architectural and technical concepts and principles of the system on a high abstraction level, covering the essential technical notion reusable across product families.
* [MBSE Methodology](mbse-methodology.md) - The MBSE Methodology is a consistent set of related processes, roles, methods, products, and tools that guides the effective application of MBSE in a complex engineering environment.
* [MBSE Training](mbse-training.md) - The MBSE Training deploys MBSE knowledge and skills to the SYSMOD roles and stakeholders of the MBSE Methodology through training sessions in different formats.
* [Physical Architecture](physical-architecture.md) - The Physical Architecture is the general term for Logical Architecture, Product Architecture, Base Architecture, and Test Architecture, representing physical elements and their arrangement.
* [Problem Statement](problem-statement.md) - The Problem Statement is a clear and concise statement of an unwelcome situation that the system of interest should resolve, describing the gap between the current state and the desired state.
* [Product Architecture](product-architecture.md) - The Product Architecture specifies the concrete physical architecture of the system of interest as the most detailed system architecture specification in the system model.
* [Requirements](requirements.md) - The Requirements specify functions, non-functional properties, or constraints that must be satisfied by the system, forming the contract between stakeholders and systems engineers.
* [Risks](risks.md) - The Risks product specifies the potential inability to achieve the System Objectives, linked to other model elements for traceability and integrated with or proxying an external risk management tool.
* [Scenarios](scenarios.md) - A Scenario describes a concrete collaboration of actors and system parts to perform a system function, verifying that all necessary parts and connections exist in the architecture.
* [Stakeholders](stakeholders.md) - The Stakeholders product is a list of all individuals and organizations who have concerns about the system that can be the source for requirements, including their concerns and prioritization.
* [System Architecture](system-architecture.md) - The System Architecture is the generic term for all architecture kinds of the system, representing the common concepts of all architecture types including Base, Functional, Physical, Logical, Product, and Test Architectures.
* [System Context](system-context.md) - The System Context lists the external entities that interact with the system and shows how the system is embedded in its environment, including system actors, interfaces, and item flows.
* [System Idea](system-idea.md) - The System Idea describes the core idea and leading features of the system as a brief elevator pitch that every project member must understand.
* [System Modeling Environment (SME)](system-modeling-environment.md) - The System Modeling Environment (SME) represents the customized setup of the systems modeling tools configured to support the MBSE Methodology and daily engineering work.
* [System Objectives](system-objectives.md) - The System Objectives represent the main objectives of the vendor or owner of the system, used to understand the rationale of requirements and communicate priorities to developers.
* [System Processes](system-processes.md) - The System Processes specify the logical order of execution of the System Use Cases, describing uses of the system on a higher level than the individual use cases.
* [System States](system-states.md) - The System States describe the relevant conditions of the system or parts of the system, acting as pre- and postconditions of functions that control behavior when events are received.
* [System Use Cases](system-use-cases.md) - The System Use Cases are a table of content of the services provided by the system to its system actors, providing an outside-in view of system functions from the perspective of system actors.
* [Test Architecture](test-architecture.md) - The Test Architecture specifies the setup of the tests and the test systems, including how the system under test is integrated into the test environment.
* [Test Cases](test-cases.md) - The Test Cases specify procedures on how to test that the system satisfies the requirements, closing the loop from requirements through the system architecture back to the requirements.
* [Use Case Activities](use-case-activities.md) - The Use Case Activities are specifications of the system functions represented by the System Use Cases, defining their functional decomposition, execution order, and object flows.
